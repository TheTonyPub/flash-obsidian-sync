## Context

See [proposal.md](proposal.md) for motivation. The plugin already requires `wss://`, derives `OBS_<vaultId>_FILES`, and opens a pre-existing bucket. Existing [NATS setup guidance](../../../docs/nats-setup.md) defines one scoped user per vault and a private WebSocket listener behind Caddy. The new tool manages user-owned infrastructure; it does not run inside the plugin. The three new specs define the external contract.

## Goals / Non-Goals

**Goals:** One interactive first-run flow on the target Debian/Ubuntu server, a reproducible unattended equivalent on that server, explicit ownership of generated resources, reliable vault isolation, and recoverable operations across native, Docker Compose, and Podman Compose installations. The plugin remains usable for inline Markdown with empty S3 settings.

**Non-Goals:** Opening SSH connections from a local machine to deploy a remote host, operating a hosted service, automatically provisioning S3, replacing NATS KV, granting plugin users administrator access, bypassing TLS verification, or modifying unrelated pre-existing Caddy/NATS deployments.

## Decisions

### Document source installation before automation

Start with a concise root README that a new user can follow without the proposed installer. Describe supported Obsidian version, required Node/npm tooling, build command, required plugin artifacts and placement at `.obsidian/plugins/flash-osidian-sync`, enabling Community Plugins, NATS WSS/bucket/user prerequisites, optional S3 behavior, and one connection check. Link to detailed NATS guidance instead of duplicating configuration. Manual installation from source is a desktop development/onboarding path; do not promise the same file-copy procedure on mobile. This documentation must be usable before any server CLI exists. Community-directory release packaging and submission remain a separate later step. Alternative: document only the installer, rejected because users need an immediate source-install path and installer development needs a working baseline.

### Preserve local state when renaming the plugin

Set the Obsidian manifest ID and display name to exactly `flash-osidian-sync` (the requested spelling). Before connecting under the new ID, detect a prior `easy-sync` install and migrate a copy of its settings, including the stable vault/device binding and SecretStorage references, into the new plugin data file. Keep legacy SecretStorage keys and IndexedDB database names readable during the transition so pending outbox operations and file identity are not lost; do not create a fresh empty outbox for an existing bound vault. Register both `flash-osidian-sync-import` and legacy `easy-sync-import` URI handlers for a compatibility window. Migration is idempotent, detects conflicting new/old settings rather than overwriting either, and retains old files/data for rollback. Test fresh install, upgrade with pending outbox, retry after interruption, and rollback to the old plugin. Do not automatically delete the old plugin directory or any legacy local data. The user must disable the old plugin before enabling the renamed one to avoid simultaneous writers.

### One desired-state model and two installation adapters

Initial support is **amd64 only** on Debian 13 (Trixie), Ubuntu 24.04 LTS, and Ubuntu 26.04 LTS. Bootstrap SHALL reject every other OS release and architecture before mutation in native and Compose modes. `fos` version `0.1.0` owns the native stock-APT compatibility lock: Debian 13 amd64 uses `nats-server=2.10.27-1+b2` and `caddy=2.6.2-12+deb13u1`; Ubuntu 24.04 amd64 uses `nats-server=2.10.7-1ubuntu0.3` and `caddy=2.6.2-6ubuntu0.24.04.3`; Ubuntu 26.04 amd64 uses `nats-server=2.10.27-1build1` and `caddy=2.6.2-14`. The Ubuntu 26.04 tuple is based on exact stock APT candidates observed on an Ubuntu 26.04 amd64 host. Every CLI release SHALL declare its own platform/package lock and reject a platform or unavailable exact package before mutation. Native mode uses only stock distribution APT repositories: no direct binaries and no third-party repositories. Container installation records both an immutable image digest and its human-readable tag. `latest` is forbidden. These are selected baselines; upgrades remain a separate opt-in operation. References: [NATS releases](https://github.com/nats-io/nats-server/releases), [NATS release support policy](https://github.com/nats-io/nats-server/blob/main/RELEASES.md), [Caddy releases](https://github.com/caddyserver/caddy/releases), and [Caddy Debian/Ubuntu installation](https://caddyserver.com/docs/install).

Support Docker only through `docker compose` (Compose v2 or v5; reject legacy `docker-compose`). Support Podman only with Podman 5.x, rootful operation for ports 80/443, and an explicitly configured `podman-compose` provider. `podman compose` is an external-provider wrapper, so bootstrap records the provider executable and version, rejects a different implicit provider, and preflights `config` plus a disposable create/up/down cycle. Generated Compose files use only the common Compose Specification subset; provider-specific extensions require a separate override and test. References: [Docker Compose history](https://docs.docker.com/compose/intro/history/), [Docker Compose on Linux](https://docs.docker.com/compose/install/linux/), and [Podman Compose](https://docs.podman.io/en/latest/markdown/podman-compose.1.html).

Provide `fos bootstrap`, `plan`, `status`, `vault create/list/inspect/rotate-password/revoke`, `backup`, `restore-check`, `upgrade`, and `uninstall`. Run the CLI as root via `sudo fos` on the target host; an operator may first open a shell there through SSH, but the CLI does not manage SSH, accept `--host`, use a remote Docker context, or execute against another host. The interactive wizard gathers installation mode, runtime, endpoint domain, first vault, optional external S3 settings, and independent operational choices. It generates administrator and vault credentials instead of asking the operator to choose passwords. It shows a redacted plan before confirmation. The unattended form is `fos bootstrap --non-interactive --input <root-readable-file> --secrets-output <owner-readable-0600-file> --approve`; it rejects missing confirmation or inputs and rejects secrets in ordinary CLI flags, shell history, logs, or generated Compose environment files. A root-owned state manifest records managed paths, versions/digests, ownership, and selected operations, not plaintext passwords. Use a single reconciler and mode-specific service adapters; reruns compare desired and actual state before mutation. Alternative: separate native and container installers, rejected because permission and drift logic would diverge.

Native mode owns only `/etc/flash-osidian-sync/{nats-server.conf,Caddyfile,state.json}`, `/var/lib/flash-osidian-sync/{nats,caddy-data,caddy-config}`, `/var/log/flash-osidian-sync`, and `fos-{nats,caddy}.service`. It treats package-manager binaries as dependencies rather than overwriteable files. Compose mode owns only `/opt/flash-osidian-sync/{compose.yaml,Caddyfile,nats-server.conf,state.json}`, the same `/var/lib/flash-osidian-sync` data roots, and optional `/var/log/flash-osidian-sync`; it fixes the project name to `flash-osidian-sync` and never sets global `container_name`. No prior managed installer has shipped, so this is not a server-state migration; if any older managed state is discovered, stop rather than silently creating a parallel installation. If an existing service occupies required ports, systemd unit names, project name, or any owned path, bootstrap stops without adopting or overwriting it. Adoption of a pre-existing Caddy/NATS installation is out of scope for this change.

Native mode uses the current CLI release's stock-APT compatibility lock for NATS and Caddy with systemd, a private WebSocket listener, and a persistent JetStream directory. It runs neither daemon as root. Preflight calls `apt-get update`, verifies each exact locked package version remains available, and only then permits `apt-get install` with exact version arguments. A dedicated account is offered if a suitable restricted service identity is not already available; native install cannot proceed without a safe identity. Compose mode uses pinned NATS/Caddy images, internal networks, persistent volumes, and a runtime-specific invocation adapter (`docker compose` or `podman compose`) with compatibility checks. Keep generated configuration inspectable and inside a root-owned installation directory. Do not assume that an arbitrary Podman Compose provider implements every Docker feature; test selected provider before applying. Alternative: build two divergent Compose templates, rejected unless compatibility testing requires narrow overrides.

Build `fos` from this repository's source on the supported target server and install the locally built package; APT is only for native NATS and Caddy dependencies. Document source installation and CLI operation separately in `docs/fos-install.md` and `docs/fos-usage.md`, and link both from the README and NATS setup guide. The install guide covers prerequisites, build, local package installation, verification, and updates. The usage guide covers the interactive bootstrap, modes, commands, and protected credential input/output.

### Existing deployment as a reference topology

The operator's current configuration is a historical compatibility reference: one domain-facing Caddy container publishes host ports 80/443; Caddy and NATS share a private Compose network; the existing NATS config has a WebSocket listener on 9222 and an HTTP monitoring listener on 8222; JetStream persists under `/data`. NATS accepts plaintext WebSocket traffic on the private network because Caddy terminates TLS. Its Caddyfile also routes `/monitoring` to the monitoring listener. This change preserves the endpoint and data-layout concepts only. Generated configuration omits the monitoring listener, the 8222 port, and the `/monitoring` route entirely; monitoring is deferred to a separate change.

This is reference input, not a template to copy verbatim. Generated configs use pinned image versions instead of `latest`, generated distinct credentials instead of the sample `pass`, and the selected domain/email instead of the example values. Every installation mode exposes only Caddy TCP 80/443 publicly. Native NATS client and WebSocket listeners bind to loopback; Compose exposes neither NATS listener on the host and keeps the NATS service on a private network. There is no NATS HTTP monitoring listener or Caddy monitoring route in this change. Model the sample `$KV.OBS_VAULT_A_FILES.>`, `_INBOX.>`, and bucket-specific `$JS.API.*` permissions as a starting point, then test the minimum effective grants against pinned NATS and client versions. Existing data and configuration are never silently adopted or overwritten.

### Domain-only verified TLS

Require a domain. Use Caddy-managed public certificates after DNS, reachability, and port checks. Never disable certificate verification or silently fall back to `ws://`. Caddy terminates TLS and proxies only to a local/private NATS WebSocket listener. Only Caddy TCP 80/443 accept public traffic; NATS client/admin access remains local or on the private Compose network. Monitoring is outside this change. References: [NATS proxy TLS](https://docs.nats.io/learn/websocket/tls-and-proxies), [Caddy HTTPS](https://caddyserver.com/docs/automatic-https).

### Separate administrator channel from plugin credentials

The operator CLI owns NATS user entries in managed configuration and reloads/restarts the managed NATS service after validating the candidate configuration. Static NATS users cannot be created merely by issuing a JetStream API call; in Compose mode, the CLI still updates mounted authorization configuration through its managed service adapter. Bootstrap creates a separate administrator identity and first-vault identity with distinct cryptographically random passwords of at least 128 bits of entropy. Bucket creation and inspection use an internal, privileged NATS connection (including inside a container network when applicable). Every later `vault` management command requires the administrator password, supplied through a hidden prompt or protected input, before KV or user mutation. No public management endpoint or plugin-side administrator credential. Use a unique normalized vault ID, reject collisions, create file-backed bucket with history 10 and replicas 1, and apply the per-vault allowlist from existing integration tests. A plugin user gets `$KV.<bucket>.>` and only necessary `$JS.API...KV_<bucket>` publish subjects plus `_INBOX.>` and scoped KV subscriptions; validate against pinned client/server versions. Store only bcrypt password hashes in managed NATS configuration. After installation and connectivity checks succeed, display the two credentials once on an interactive TTY, identifying administrator versus plugin use. For noninteractive mode, atomically write them only to the operator-selected owner-readable file with mode `0600`; never print them to general automation logs. Reruns do not regenerate or redisplay existing passwords. Generate replacement vault passwords during rotation, then verify the new credential before ending the operation. Existing sessions may need explicit disconnection/reconnect; report that clearly. Alternative: NATS operator JWT management, rejected for first version because it changes the current username/password trust model.

### Explicit optional operations, separate from basic bootstrap

Firewall management is opt-in and must first identify SSH access and preview all changes; never assume port 22. Backup setup is opt-in with an operator-chosen destination, retention, encryption/access policy, and periodic restore checks. Upgrade management is opt-in; pin versions, back up state, validate config, apply one service at a time, health-check, then roll back on failure where safe. Uninstall *support* is selectable at bootstrap; running uninstall later is never part of bootstrap. Uninstall previews resources, preserves JetStream data, backup, and CA by default, and requires a separate typed confirmation for optional data deletion. S3 remains external; the installer does not install it. Alternative: own all host operations by default, rejected for SSH lockout and data-loss risk.

### Plugin behavior without S3

Allow all S3 fields to remain empty in plugin settings. A NATS-only connection still syncs inline Markdown. Without S3, do not upload images or publish KV records that claim an image blob exists. Keep image changes local and report them as not synced, without blocking unrelated Markdown. When the operator later adds valid external S3 settings, resume pending image transfers. Keep existing hash verification for downloaded blobs. Apply the same no-loss rule to any other file that requires blob storage, including oversized Markdown; do not silently drop or mislabel it. Alternative: refuse plugin setup until S3 exists, rejected because S3 is optional for the requested Markdown-only mode.

### Verification and packaging

Build requirement-derived failing tests first: documentation checks for a reproducible source install, server-local CLI preflight, wizard and unattended input, idempotent plan, native and two Compose adapters, domain certificate checks, generated credentials and protected handoff, administrator-gated KV commands, user/bucket grants, cross-vault negatives, rollback, backups, and plugin operation with empty S3 settings. Use disposable NATS+Caddy integration environments and Debian/Ubuntu VM/container smoke tests. Extend `.gitignore` for `.DS_Store`, local environment/secret files, generated deployment data, and logs while preserving checked-in examples/templates. Keep docs in English, including updates to the current NATS guide.

## Risks / Trade-offs

- Domain DNS or public certificate issuance can fail. Mitigation: preflight and refuse to report endpoint readiness until verified WSS succeeds.
- Podman Compose providers differ. Mitigation: preflight capabilities and exercise both runtimes in separate integration jobs.
- Host firewall changes can sever SSH. Mitigation: opt-in preview, active-port confirmation, staged rules and recovery instructions.
- Native NATS user edits need config reload; KV API alone cannot add users. Mitigation: validate and atomically replace managed config, reload, verify, restore previous config on failure.
- Partial vault provisioning can leave a bucket without a usable user. Mitigation: record staged operation, retry safely, never delete bucket to compensate.
- A process failure before one-time credential handoff or loss of the administrator password can block later KV management. Mitigation: retain data, report an explicit server-local administrator recovery path, and never silently regenerate credentials on rerun.
- Backups may be incomplete or untested. Mitigation: explicit retention and restore verification; never claim disaster recovery from an unchecked local copy.

## Migration Plan

1. Publish and verify the root README's source-build and manual-install path before implementing the server CLI.
2. Ship CLI and updated server setup documentation without changing plugin connectivity. Existing manual installations remain supported; do not adopt them automatically.
3. On a fresh Debian/Ubuntu host, run the CLI on the server, select mode and domain, preview plan, bootstrap services, verify WSS, provision the first vault, receive generated credentials through protected output, retain the administrator password for later KV management, then enter only the vault password into Obsidian SecretStorage-backed settings.
4. For an existing unmanaged installation, report ownership and port conflicts without adopting or overwriting it. Existing manual deployments remain operational; migration to managed resources requires a separate, explicitly designed change. On failure restore prior owned config/service state, retain JetStream data, and report manual recovery steps.
5. Upgrade and uninstall act only on resources recorded as owned. Uninstall keeps data, certificates, and backups unless separately confirmed for deletion.
