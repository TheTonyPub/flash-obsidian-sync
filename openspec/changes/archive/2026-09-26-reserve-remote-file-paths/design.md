## Context

See [proposal.md](proposal.md). Remote file records remain `f.<fileId>` in each vault's KV bucket, with inline Markdown or a hash-addressed S3 blob reference. The first two changes establish ordered path reuse and avoid scans for ordinary same-path edits. This change replaces the remaining full collision listings for path claims. The [final architecture](architecture-after.md) shows all three changes together.

## Goals / Non-Goals

**Goals:** One authoritative owner per normalized path; bounded create/rename checks; safe retries and recovery at every multi-key interruption; preserve content and genuine conflict reporting.

**Non-Goals:** META/BLOB KV bucket split, reconnect cursor, production data migration, or server deployment.

## Decisions

1. **Canonical path key.** Define a deterministic, locale-independent path canonicalizer: existing path normalization, Unicode NFC, separator normalization, then a pinned Unicode case-folding table/version shared by Desktop and Mobile. Hash the canonical UTF-8 bytes with SHA-256 to form `p.<hex>`, a NATS-safe bounded key. Store the canonical path in the value and verify it on read; a mismatched value is an integrity error, never an alias. Case-only rename keeps the same key and `fileId`; update the display path in `f.<fileId>`. Alternative: `toLocaleLowerCase()` can vary by locale; raw path keys can exceed KV key restrictions.
2. **Ownership state in the existing vault bucket.** `p.<hash>` contains canonical path, `fileId`, operation ID, and state `reserved | owned | released`; KV revision is the CAS token. Released entries remain as values so reclaims use CAS of their current revision; a missing key uses create. `owned` is the committed path owner. `reserved` blocks a competing identity while a multi-key operation is incomplete. File records stay under `f.<fileId>`; watches and full reconciliation filter `f.` keys before decoding file records. Alternative: a separate bucket adds permissions and lifecycle complexity without need here.
3. **Claim before file publication.** For create or rename, CAS a released/missing destination into `reserved` for the operation, or reuse an identical reservation on retry. A reservation/ownership for another live `fileId` is a collision; preserve local bytes via the existing conflict flow. Then CAS `f.<fileId>` with the new path and operation ID, CAS destination to `owned`, and only then CAS the old path to `released`. Hold later operations for that same `fileId` until finalization, so its `f.` operation ID remains available as recovery evidence. A case-only rename skips the new reservation because the key and owner are unchanged. A delete first CASes `f.<fileId>` to a tombstone and then releases that file's owned path. Each step is idempotent from operation ID, file ID, and current KV revisions. Alternative: update `f.` first leaves a window where another file can claim the path.
4. **Recovery follows durable evidence.** Keep operation intent in the IndexedDB outbox until all relevant KV states are complete. On retry after a crash, read the specific `f.` and `p.` keys, then resume the missing CAS step. Any peer may finalize `reserved → owned` when `f.` already names the same path, `fileId`, and operation ID, or release an obsolete old owner once `f.` no longer names that path or is tombstoned. A reservation whose `f.` still points elsewhere is retained for the original durable operation to resume or explicitly abort using its own CAS revision; other replicas do not steal it based on a clock. If the originating operation never returns, report the blocked path for owner recovery or an explicit development reset rather than silently assigning it to another `fileId`. Alternative: automatic time-based lease expiry cannot fence an in-flight `f.` CAS and risks duplicate ownership.
5. **Recheck on CAS races.** Any failed `p.` or `f.` CAS reloads the current entries and classifies success, retry, or genuine conflict; it does not overwrite by last writer time. If an `f.` CAS loses, the operation releases only its own still-matching reservation, retaining local bytes for merge/conflict handling. Preserve the first change's A-delete-before-B dependency: B can claim A's released path only after A's remote tombstone, and can repair A's stale `p.` entry from that tombstone.
6. **Permissions and rollout.** Add `p.>` read/write subjects to the per-vault user-run NATS setup reference; `f.>` watch remains the file-record feed. During development, reset only an explicitly selected disposable test vault or a selected vault with exported/backed-up files and a verified clean sync state. Never clear local sync state or the outbox while pending changes or unresolved conflicts remain; resolve or preserve them first. No automatic production migration or mixed-client compatibility path is planned.

## Risks / Trade-offs

- [Crash leaves `reserved` while origin stays offline] → Keep it blocked and visible; resume from durable outbox on origin reconnect. No clock-based seizure.
- [Interrupted rename leaves both old and new path keys occupied by one file] → Recover from the current `f.` path and CAS-release only the obsolete key.
- [Different Unicode/case behavior across clients] → Share a pinned canonicalizer and verify vectors on Desktop and Mobile before rollout.
- [Legacy development bucket lacks `p.` entries] → Require explicit selected-vault reset/rebootstrap with exported or backed-up files and verified zero pending operations and unresolved conflicts. A disposable test vault can instead be discarded as a whole. Do not infer ownership from a partially populated index.
- [NATS KV allows no cross-key transaction] → Reserve first, keep operations idempotent, and test interruption after every CAS boundary. A pending reservation is unavailable to other identities until recoverable evidence resolves it.

## Migration Plan

Development-mode reset/rebootstrap is the selected rollout. The user-run procedure must name the selected vault, export or back up its local files, verify no pending outbox operations, no unresolved conflicts, and a reconciled state, then clear that vault's remote KV and matching local sync state and repopulate `f.` and `p.` together. If pending changes or conflicts remain, halt the reset until they are resolved or separately preserved; never clear the outbox in that condition. An explicitly disposable test vault may instead be deleted wholesale rather than represented as a data-preserving rebootstrap. Server operations remain user-owned. Runtime retries and interruption recovery are still required after rollout.
